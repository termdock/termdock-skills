# Persisted AST index compatibility

`ast:index-status` and successful `ast:list-files` may return `compatibility` with `state`, `reason`, `schemaSupported`, and `usable`. `current` means the schema and extraction identity match; it does not mean the workspace files have been verified against disk. `supported-stale` means the schema is readable but the extraction identity is missing, different, or cannot be verified, including an unexpected Rust or supported-grammar fallback during indexing. Normal mode rebuilds schema or fingerprint mismatches through the existing indexing path. Automatic queries and warmup may retry an unverified index once per workspace per AST worker process. After an idle worker is released, the next worker can retry once again. If that attempt fails, later automatic calls in the same process do not retry again. A complete degraded index still in memory can be queried with a `supported-stale` warning; if no usable index is loaded, AST queries report `INDEX_NOT_BUILT` and `ast:search` exposes the error message. Run `termdock tool ast:build-index --workspace-path <path>` to retry explicitly even after the automatic retry is spent. A read-only code-graph MCP can read supported stale data without writing or starting a full rebuild. `unsupported` cannot be loaded, including in read-only mode.

`ast:index-status` can also return `extractorFingerprint`, the running service process identity. If browser-process disk inspection cannot reach the service, the extractor is unverified rather than inferred from the browser process. `ast:search` and AST query metadata may also include `compatibility`. The standalone code-graph MCP adds a separate `content` item to successful queries when compatibility is stale or unknown. Check all `content` items, not only the first. `termdock_status` reports it under `index.compatibility`; `termdock_files` reports it in its result.
